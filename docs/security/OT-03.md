# OT 03 Integridad de calificaciones y cálculo en servidor

Responsable: Christian Salas. Módulo: Operación y transacciones.

## Problema

En fase 2 se persistieron `calculated_marks=999` y `final_marks=999` con una escala de control de 0 a 100. El flujo copiaba `calculated_mark` desde el navegador. Las notas individuales tampoco se comparaban con el máximo del examen. La evidencia anterior está en `06_nota_final_fuera_rango.json` y `07_despues_nota_final.json`.

Clasificación: OWASP A06:2025 Insecure Design. Referencias de fase 1: R-OT-01, R-OT-05 y CTRL-OT-02; NIST CSF 2.0 PR.PS-06. El control de autorización por contexto complementa PR.AA-05.

## Corrección

- `MarkValidation` valida valores numéricos finitos y compara cada nota individual con cero y el máximo de su regla de examen. Cada examen requiere exactamente una regla válida. Una regla ausente, duplicada o inconsistente produce un rechazo 422 y debe corregirse antes de enviar calificaciones.
- La nota calculada se obtiene en el servidor sumando las notas persistidas de todos los exámenes del curso, clase, semestre y sesión, para el alumno y sección autorizados. Se conserva la suma utilizada por la vista existente y se redondea a dos decimales; no se introduce una fórmula de ponderación nueva. El campo `calculated_mark` del cliente se ignora y puede omitirse.
- Para enviar notas finales deben existir notas únicas y válidas para todos los exámenes del curso. Los datos heredados incompletos, duplicados o fuera de rango se rechazan en vez de consolidarse.
- La calculada y la final deben pertenecer a un intervalo válido de la escala de calificación del contexto. Se utiliza la escala configurada, no un máximo fijo 100. Si la suma de exámenes no encaja en esa escala, se rechaza el envío para revisar los datos o la configuración.
- Se conserva el ajuste manual que ya permite la aplicación, dentro de la escala, pero se exige una explicación cuando difiere de la calculada. El observador existente registra el actor y los valores del nuevo `FinalMark`.
- `StoreFinalMarksRequest` exige el permiso `save marks`. La ruta comprueba la asignación del docente, la matrícula, el contexto y la ventana de envío. El formulario de consulta final recibe el mismo control de acceso.
- El lote de notas finales se valida antes de escribirse y se guarda dentro de una transacción. Los registros de matrícula y notas se consultan con bloqueo para coordinar las escrituras. Se rechaza repetir una nota final ya enviada y modificar sus notas individuales después del envío.

## Reproducción

Con las dependencias de desarrollo y una APP_KEY de pruebas configurada:

```sh
php vendor/bin/phpunit --filter MarkValidationTest
php vendor/bin/phpunit --filter 'CourseMarkAccessTest|MarkStoreAccessTest|MarkValidationTest'
```

Los datos se crean con `RefreshDatabase` y SQLite en memoria. La ejecución se realizó en PHP 7.4 dentro de un contenedor sin red, sin usar la base ni reemplazar los archivos de evidencia de la fase 2. No se verificó concurrencia real de MySQL mediante estas pruebas.

## Casos de regresión

La prueba específica cubre el valor 999; números negativos, no numéricos y desbordamientos; máximos de examen y límites válidos; cálculo desde datos guardados; suma de varios exámenes; ajustes manuales y actor de auditoría; escalas distintas de 100 y huecos entre intervalos; reglas ausentes, duplicadas o inválidas; notas de origen inválidas, faltantes o duplicadas; lotes inválidos y fallos de escritura sin persistencia parcial; alumnos y contextos ajenos; permisos, asignación y ventana; reenvío y cambios posteriores; formulario autorizado y acceso anónimo.

La prueba anterior de OT-02 incorpora reglas de examen en su fixture para mantener un contexto académico válido. No se elimina ningún caso de autorización existente.
